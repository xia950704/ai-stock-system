# P0 验收标准（acceptance-tests）

> 生成时间：2026-10-20。P0 只读探查产物。
> 本文件列出 P1 及以后阶段的验收标准和测试方向，供后续阶段参考。
> P0 阶段自身无需执行这些测试，仅作规划。

## 1. 验收范围与原则

- **P1 验收**：以文件迁移完整性、引用可解析、无写回源数据为核心。
- **P2 验收**：重点在代码健壮性、异常处理、测试覆盖、工作流可靠性。
- **P3 验收**：JEV 集成后的判断准确性、错误降级、报告可溯源。
- **P4 验收**：影子运行与历史回溯、长期稳定性。

所有验收必须能够给出可重复执行的检查步骤，并给出通过/失败的明确标准。

## 2. P1 验收标准（文件迁移与引用）

| 项 | 检查点 | 通过标准 |
|---|---|---|
| F1 | 所有从 Obsidian 复制的文件是否保留内容不变 | 源与目标 sha256 一致 |
| F2 | 所有复制文件是否写入目标目录（如 src/、docs/） | 目标存在且非空 |
| F3 | 是否有任何写回 Obsidian 原始文件的痕迹（如改动时间戳、内容） | 对比源文件在迁移前后的 git diff 为空（或文件未变） |
| F4 | 关键脚本中的硬编码绝对路径是否已替换 | 搜索 `\/Volumes\/夏爽\/`、`\/Users\/xiashuang\/harness\/`、`\/Users\/xiashuang\/obsidian\/` 等绝对路径，必须为零 |
| F5 | 迁移清单中的 hash_sha256 与实际文件一致 | verification 列为 verified |
| F6 | 目标目录结构是否符合 architecture-proposal.md 的建议 | 目录层级、命名约定基本匹配 |
| F7 | 迁移后，Hermes cron 与 GitHub workflow 能否正常触发（不必检查产出） |  cron 显示 enabled，且 last_run_at 有最近时间（非永久停止） |
| F8 | 是否存在明显的重复文件未处理（如同名文件出现在两处） | 内部文件路径唯一，或重复有明确说明（如存档） |

## 3. P2 验收标准（代码质量与测试）

| 项 | 检查点 | 通过标准 |
|---|---|---|
| C1 | 数据抓取脚本能否在单元测试中模拟成功与失败场景 | 80%+ 行覆盖率，关键路径有断言 |
| C2 | 数据清洗脚本能处理缺失值、异常值、时间错位 | 提供测试用例：空文件、缺列、重复行、非法日期 |
| C3 | 因子计算脚本（如 GF-DMA、排名）输出是否可重复 | 给定相同输入，输出bit-wise 一致 |
| C4 | 报告生成脚本输出是否包含必备元素：结论、数据日期/来源、文件链接 | 抽样检查报告 frontmatter 或正文 |
| C5 | JEV 客户端封装能否正确处理成功、超时、非200、解析错误 | mock 网络响应，断言返回结构 |
| C6 | 工作流调度（如 cron jobs.yaml）是否能被解析并触发正确脚本 | 单元测试加载 jobs.yaml，检查任务与时间 |
| C7 | 日志是否能够记录关键操作（抓取开始/结束、判断输入输出） | 检查日志文件非空且含预期关键字 |
| C8 | 是否有明显的死循环或资源泄漏（如未关闭文件句柄） | 粗测试：运行 10 分钟无内存异常增长 |
| C9 | 测试覆盖率（行覆盖）是否达到合理阈值 | 总体行覆盖率 ≥ 70%，关键模块 ≥ 80% |
| C10 | 是否禁止使用 `shell=True`、`eval()`、`exec()` 对外部输入 | 代码审计无误用 |

## 4. P3 验收标准（JEV 集成与判断）

| 项 | 检查点 | 通过标准 |
|---|---|---|
| J1 | JEV 调用封装是否能正确返回 choice/score/noul 及其字段 | 单元测试覆盖三种题型 |
| J2 | 在分析流程中调用 JEV 后，结论中是否标注“JEV 辅助：……” | 抽样检查报告中含该字样 |
| J3 | JEV 调用失败时，系统是否降级为仅规则判断并明确标注 | 故障注入网络不可达，检查日志与结论 |
| J4 | JEV 判断的置信度或概率是否被用于决策阈值（如只有 confidence > 0.8 才采纳） | 检查代码中是否有置信度阈值逻辑 |
| J5 | 是否存在将 JEV 输出误认为确定性结论的代码（如直接用 choix 作为买卖信号） | 代码审计无此模式 |
| J6 | JEV 调用频率是否受保护（如防止因循环导致过度调用） | 检查是否有调用计数器或频率限制 |
| J7 | 是否提供 JEV 调用的输入输出日志（便于审计） | 日志中含 state、questions、model、output、timestamp |

## 5. P4 验收标准（影子运行与历史回溯）

| 项 | 检查点 | 通过标准 |
|---|---|---|
| S1 | 选取历史交易日（如 2026-09-01 至 2026-09-30），使用相同数据运行新旧系统，判断是否有实质性出入口 | 新旧系统结论趋势一致，重大分歧须有说明 |
| S2 | 故障注入：行情数据缺失一天，系统是否停止产出判断而非编造数据 | 检查日志与报告是否明确标注数据缺失 |
| S3 | 故障注入：JEV MCP 长时间超时，系统是否继续输出仅基于规则的判断 | 检查结论中是否有“JEV 不可用”标注 |
| S4 | 是否保留运行日志与数据版本，防止旧报告被误认为新证据 | 日志中含 Git SHA 或数据时间戳 |
| S5 | 是否有明显的保留偏差（如新系统总是更乐观） | 需要统计检验，若存在须说明原因 |

## 7. 结束语

本验收标准旨在确保系统在逐步迁移过程中保持数据安全、功能不回退、判断可溯源。P0 产物仅为规划与探查，真正的验收将在 P1 及以后通过实际操作与测试完成。请在各阶段根据本文件进行自检，并保留验收记录以供审计。
